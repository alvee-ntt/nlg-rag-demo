How the client facts flow works

When an agent describes a specific client, Ask Navigator collects the facts the underwriting guide treats as material, asks for what is missing, and answers with what the guide lays out for those facts. This page explains what happens on each message.

The short version

Every message is classified once. Only messages about a specific client enter the client-facts path. Inside that path the model does two jobs; everything else is lookup code against a rulebook extracted from the guide.

The model model call

  • Decides whether a message is about a client or a replacement
  • Turns the agent's sentence into rulebook keys
  • Writes the final answer, through the hosted Foundry agent

The rulebook lookup code

  • Which facts are required, and their answer options
  • Which questions to ask, and why each matters
  • Every line under "What the underwriting guide says", with its page

Each missing fact can hold up an answer only once. After the card has asked for it, later turns answer with what is known.

One client, turn by turn

  1. The agent types: "Client is 46, takes metformin for type 2 diabetes. Looking at FlexLife for family protection."

    The classifier flags the message as about a client. The extractor returns age 46, the medication, the need, and the condition type 2 diabetes.

    2 model calls

  2. The server works out what is missing.

    Required facts are the four universal ones (age, coverage amount, tobacco, height and weight) plus what the rulebook lists for type 2 diabetes. Seven are unknown and none has been asked, so it returns the facts card and does not call the agent.

    lookup only

  3. The agent taps "Walk through questions with client".

    The stepper runs in the browser from the question list that came with the card. On finish, the browser writes the answers onto the sheet and sends one summary message marked as hand-entered.

    no server call per question

  4. The server answers.

    It skips extraction because the facts are already structured, runs the guide lookups, and calls the agent with the facts as context. The reply carries the agent's answer plus the guide block, and the card above fills in.

    classifier + agentguide lookup

  5. A follow-up: "Does he need an exam?"

    It goes to the agent with the same facts. The guide block is not repeated, because the sheet did not change.

  6. "They want to cash out a whole life policy to pay for this."

    This takes the replacement branch: a state-rules banner, the existing "Ask NLG for a decision" handoff, and a "Back to the client" chip that redraws the card with no model call.

Example, shortened. The real card lists all seven missing facts.

Where the rows come from. The known rows are what the extractor found. The missing rows are the rulebook's required facts that are not on the sheet yet.

Where the questions come from. Each missing fact has a question, answer options taken from the guide's own cut-offs, a reason, and a page number, for example the requirements grid on p.23.

What it never does. It collects and explains the information underwriting needs. It does not say whether a client will be approved or name a rate class for them.

Design choices behind it

The browser holds the sheet.
The server keeps no client state. It re-validates the sheet against the rulebook on every turn and drops any key it does not recognise, so there is no slot for a name or an SSN.
The model never decides what matters.
It only maps sentences to rulebook keys. Required facts, answer options and guide findings all come from the rulebook, so they are the same every time and can be reviewed.
Ordinary questions are untouched.
Client detection is folded into the domain check that already ran on every message, so a general question makes no extra model call.
Failures fall back to normal chat.
If the classifier or the extractor errors, the turn is treated as an ordinary question.
For developers

Integrating with your own changes

The whole feature rides on the existing POST /v1/foundry/chat endpoint. There is no new endpoint, table or dependency. Every new field is optional, so a client that ignores them sees the same behaviour as before.

Request, two new fields

  • case: the sheet the server returned last turn, or null
  • case_action: "answers" when the sheet was filled in by hand, "answer_now" to skip the questions, "show" to redraw the card with no model call

Response, new fields

  • case: the updated sheet; store it and send it back
  • case_card: show, rows, questions, edit_questions, note
  • findings, fit_signals, actions, disclaimer, banner, underwriting

If you are changing the chat path.
All branching is in service.chat_foundry, after the domain check. A turn that is not about a client returns early through the same agent call as before, so changes to the ordinary path do not need to know about any of this. classify_domain still exists as a wrapper, but chat_foundry now calls classify_turn.
If you are building a different front end.
Draw case_card.rows when show is true. To collect answers, write { value } or { status: "skipped" } into case.facts under each question's key and send the next message with case_action: "answers". The server recomputes every display string, so the client does not need to format values.
What to run.
tests/test_m16_rulebook.py covers the rulebook and lookups; tests/test_m16_client_facts.py covers every branch of the chat path with the model and agent mocked. Run the suite inside the app image, because the endpoint tests do not run on the host Python.

What carries over to a multi-agent workflow

The feature is already split along the lines a multi-agent design wants: one routing step, one intake step, a set of deterministic lookups, and one answering step, all passing a single validated state object. The lookups move across unchanged. The glue that sequences them does not.

Piece todayRole in a multi-agent designReusable as is?
Case sheet + clean_caseShared workflow state, validated at every hand-off so no agent can add a key the rulebook does not defineYes
missing_keys, unasked_missing, questions_forA "what should I ask next" tool for an intake agentYes. Pure functions, no model or database
findings_for, requirement_code, financial_requirements, income_multipleGuide-lookup tools for an underwriting agent. They return cited facts, so the agent does not have to recall the gridYes
context_textThe guardrail and facts block for whichever agent writes the answerYes, as text
Rulebook JSONThe knowledge those tools read. Also usable directly as a tool schema: each fact has a type, options and a pageYes
extract_case_factsThe intake agent's extraction step, or a tool it callsMostly. The prompt is built from the rulebook; the model client is this repo's Azure OpenAI helper
classify_turnThe orchestrator's routing decisionAs a reference. An orchestrator will usually route itself
Replacement branchA hand-off to a compliance or support agentThe trigger and wording, yes. The sequencing, no
service.chat_foundryBecomes the orchestratorNo. This is the part to rewrite
Card, stepper, edit sheetThe human-in-the-loop step when an agent needs facts from the userThe JSON contract, yes. The UI code is inside one large file
The rule worth keeping.
Agents may read facts and call the lookups, but they should not decide what is material or state an outcome. Today that is enforced by the rulebook owning the required facts and by the instruction in context_text. In a multi-agent design, keep the lookups as tools and keep that instruction on the answering agent.
What needs work before reuse.
The loader reads one rulebook by file name, so a second product needs a product parameter. A few rules are written in underwriting.py instead of the JSON, including the insulin and tobacco records rule. The script that generated the rulebook from the guide PDF is not in the repository yet.
A sensible first step.
Import underwriting.py and call merge_extracted, missing_keys and findings_for directly with a hand-written sheet. They have no dependencies beyond the JSON file, so this works before any agent framework is chosen.
